# Formloom

A CPU-first, non-neural procedural still-life generator. Images are constructed from geometry, gradients, authored scene rules and seeded detail—not models, stock images or downloaded textures.

## Current capability

The desktop UI drives the Core scene generator and the Skia CPU renderer through one prompt-to-PNG path:

- Prompt, editable unsigned 64-bit seed (default `42`), Randomize, variation slider (default 35%), Generate, preview and Save PNG.
- One to three objects on the wooden table: the six fruit descriptors and six ceramic vessel descriptors (`a blue ceramic bowl`, `a cream ceramic cup`, …). One fruit may also be placed inside one bowl (`a red apple in a blue ceramic bowl on a wooden table`), one cup may hold one still beverage (`a blue ceramic cup filled with coffee on a wooden table`), and one vase may hold one tulip — red or yellow (`a red tulip in a blue ceramic vase on a wooden table`). Parsing tolerates case, whitespace and terminal punctuation; anything else is rejected explicitly.
- Generation runs off the UI thread. Duplicate actions are guarded; failed prompts retain the previous image. Preview metadata and save filenames describe the last successful generation, even if the controls are subsequently edited.
- Save PNG opens PhotinoX's asynchronous native save dialog and writes the generated bytes, not a screenshot. Cancellation retains the image. Subject tokens are whitelisted: `formloom-apple-seed-42.png`, `formloom-pear-seed-42.png`, `formloom-ceramic-bowl-seed-42.png`, `formloom-fruit-group-seed-42.png`, `formloom-ceramic-group-seed-42.png`, `formloom-still-life-group-seed-42.png`, `formloom-apple-in-blue-bowl-seed-42.png`, `formloom-coffee-in-blue-cup-seed-42.png`, `formloom-red-tulip-in-blue-vase-seed-42.png`. Filenames must end in `.png`; save errors are reported without stack traces, and technical details are logged.
- Default output is 1024 × 1024. Core supports dimensions of 64–4096 and finite variation in 0–1. Geometry uses normalized coordinates; higher variation scales bounded offsets, rather than changing the subject.

## Layout

Source projects live under `src/`, test projects under `tests/`; the repository root keeps only the solution and shared configuration.

- `src/Formloom.Core`: immutable scene types, validation, prompt parsing, PCG32, stable UTF-8 FNV-1a named random streams and scene construction. Scenes hold one to three typed items — `FruitInstance` (apple/pear/orange) and `CeramicInstance` (bowl/cup/vase with a blue or cream glaze) — exposed together through the closed `SceneEntry` projection, plus normalized vessel profiles, attachment-aware bounds and deterministic layout (`FruitComposition` for fruit-only scenes, `MixedComposition` when a vessel is present) plus the single explicit containment value `BowlContainment` (bowl + content). No rendering or UI dependency.
- `src/Formloom.Rendering.Skia`: disposable CPU raster resources, procedural setting/table, fruit bodies with stems/leaves/calyx, ceramic bodies with rims, cavities and cup handles, shared shading, shadows and PNG encoding. Contained scenes draw the bowl in full, then the content clipped against the bowl's near-wall band, so the vessel stays pixel-identical to a standalone bowl. Returns dimensions, PNG bytes and a whitelisted subject token.
- `src/Formloom.Desktop`: PhotinoX.Blazor executable, UI, generation orchestration and native PNG save service.
- `tests/Formloom.Desktop.Tests`: headless interaction/session, generation-service and PNG writer tests; references Desktop without starting the native window.
- `tests/Formloom.Tests`: Core and renderer tests, including PCG reference values, independent streams, PNG decoding/sizes, rendered-pixel repeatability and seed differences. Does not reference or launch Desktop.
- `Formloom.slnx`, `Directory.Build.props`, `Directory.Packages.props`, `.editorconfig`, `global.json`: solution and shared configuration.
- [`.agents/todo.md`](.agents/todo.md): implementation plan and outstanding acceptance criteria.

## Prerequisites and commands

Use the latest installed **.NET 10 SDK** servicing release (C# 14); a runtime alone is insufficient. Restore needs NuGet connectivity. The Windows desktop host requires **Microsoft Edge WebView2 Runtime**.

From the repository root:

```sh
dotnet restore Formloom.slnx
dotnet build Formloom.slnx --configuration Debug --no-restore
dotnet build Formloom.slnx --configuration Release --no-restore
dotnet test --solution Formloom.slnx --configuration Release --no-build --report-trx --results-directory TestResults
dotnet run --project src/Formloom.Desktop/Formloom.Desktop.csproj --configuration Release
```

The native window is titled **Formloom** and starts at 1400 × 900. Startup uses the upstream PhotinoX.Blazor 5.3.5 API with an STA entry point and explicit application disposal. The package exposes the `Photino.Blazor` namespace but is **PhotinoX.Blazor**, not the original package. Static content is copied for build/publish and resolved from the executable directory.

## Windows acceptance check

1. Launch, check styling and keyboard focus, then generate the default prompt with seed 42 and 35% variation. Verify a recognizable apple, table grain, coherent lighting and contact/cast shadows.
2. Generate the same values again; verify the same image. Randomize the seed, then generate; verify a coherent difference. Compare low/high variation and red/green/yellow prompts.
3. Enter an unsupported prompt or invalid seed; verify an actionable error and that the last image remains visible.
4. After successful generation, edit the controls without generating. Save PNG; confirm the filename still uses the displayed image's seed, not the ungenerated controls.
5. Exercise Save cancellation and a save failure. Save successfully, then open the PNG in an independent viewer and verify 1024 × 1024 dimensions.
6. Resize the window, close it and relaunch; check for UI/startup/shutdown errors.

## Phase 5: fruit containment in ceramic bowls (complete; Release CI verified, sheet reviewed)

The first spatial relationship: one existing fruit placed **inside** one existing bowl. The bowl is the container and the fruit is its content, not two neighbours that happen to overlap.

```text
<one fruit descriptor> in <one bowl descriptor> on a wooden table
```

| Fruit descriptors | Bowl glaze | Example | Subject token |
| --- | --- | --- | --- |
| `a red apple`, `a green apple`, `a yellow apple` | blue / cream | `a red apple in a blue ceramic bowl on a wooden table` | `apple-in-blue-bowl`, `apple-in-cream-bowl` |
| `a green pear`, `a yellow pear` | blue / cream | `a green pear in a cream ceramic bowl on a wooden table` | `pear-in-blue-bowl`, `pear-in-cream-bowl` |
| `an orange` | blue / cream | `an orange in a cream ceramic bowl on a wooden table` | `orange-in-blue-bowl`, `orange-in-cream-bowl` |

Twelve combinations: six fruit descriptors × two bowl glazes. The order is significant — the fruit is the content, the bowl is the container — and `in` is the only supported relationship word. Case, whitespace and terminal-punctuation normalization are unchanged.

Rejected by design, with the whole prompt refused rather than simplified:

- `in` with any other vessel: `a red apple in a blue ceramic cup on a wooden table`.
- Reversed or alternative wordings: `a blue ceramic bowl with a red apple`, `a blue ceramic bowl containing a red apple`, `a blue ceramic bowl with an apple inside`.
- Plurals, quantities and extra adjectives: `two red apples in …`, `a big red apple in …`, `a large blue ceramic bowl`.
- Multiple fruits or bowls, nesting (`… in a blue ceramic bowl in a cream ceramic cup on a wooden table`) and containment mixed with any other object in the same prompt.
- Missing `ceramic`, other colours, other vessel names and unsupported fruit (`an apple`).

Model and layout: `BowlContainment(bowl, content)` is the only containment value; it keeps the existing `FruitInstance`/`CeramicInstance`/`SceneEntry` types untouched and adds no scene graph, registry, `object` field or reflection. The content's transform is derived in bowl-local normalized coordinates (`BowlContainmentPlacement`): height as a per-fruit share of the bowl height (apple 64%, pear 74%, orange 60%), width from the fruit's own species aspect so the silhouette is never stretched, base seated just below the near rim so the front wall hides the lower 30–42%, and a small bounded horizontal drift that keeps a margin inside the inner width at variation 0 and 1. Placement consumes one dedicated stream (`containment.placement`) and the content seed comes from a separate `containment.content` stream, so changing only the bowl glaze reproduces the same fruit shape and surface detail.

Rendering reuses the existing fruit body, material, stem/leaf/calyx and detail code with the bowl-local transform. The bowl is drawn complete — rear rim, cavity, far-wall sheen, front lip, foot and outline — then the fruit is drawn and clipped against the bowl's near-wall band, so the rear rim/cavity sit behind the content and the front wall/lip occlude it. Because nothing is repainted, every bowl pixel outside the content and the cavity is identical to a standalone bowl. A subtle contact shadow is clipped to the cavity around the seated base; the contained fruit casts no tabletop shadow, while the bowl keeps its existing contact and cast shadows. Silhouette convention: a bowl with contents is one opaque shape — the mouth is an opaque interior surface and only the part of the content above the rim adds to the silhouette.

Automated coverage: twelve-combination parser/generator tests, rejection matrix, bowl-local bounds and species-aspect invariants, seeded determinism, glaze-independence of the content seed, layer/occlusion/leak/backdrop invariants against a standalone-bowl reference, empty shadow mask for the content, cavity-clipped contact shadow, silhouette convention, diagnostic passes, desktop pipeline and rendered-component prompts, and preview retention for rejected containment prompts. With `FORMFLOOM_EXPORT_ALL=1` the export tests also write `formloom-containment-*.png`, `-silhouette.png` and `.timing.json` sidecars; routine CI keeps `formloom-containment-sheet.png` (a plain row-major grid), `formloom-containment-sheet.timing.json` — the manifest that identifies every cell, since the CI image has no font stack and the sheet is not text-labelled — and the canonical case.

Status: merged as [`ed99fee`](https://github.com/Vraxo/Formloom/commit/ed99fee442da6664e201129e73535a4b96a88c44) (PR #29) with post-merge run [42034266225](https://github.com/Vraxo/Formloom/actions/runs/42034266225) green, and the review sheet inspected cell by cell afterwards — pass, with two noted cosmetic limits (the blue bowls' far inner wall desaturates to a pale grey band, and large fruits sit snug at the top of the fit range). See the [Phase 5 handoff](docs/containment-handoff.md) for design decisions, evidence, the visual review and limits, and the [checklist](.agents/todo-5.md).

## Phase 6: still coffee or tea in ceramic cups

One existing cup containing one still beverage. Four combinations: blue and cream cups, each with coffee or tea.

```
a blue ceramic cup filled with coffee on a wooden table
a cream ceramic cup filled with coffee on a wooden table
a blue ceramic cup filled with tea on a wooden table
a cream ceramic cup filled with tea on a wooden table
```

Grammar is exact: `<blue|cream> ceramic cup` + `filled with` + `<coffee|tea>` + `on a wooden table`. Case, whitespace and terminal punctuation are normalized as before. Rejected whole rather than simplified: bowls and vases as the container, `with` / `containing` / `holding` / `of` instead of `filled with`, the reversed `coffee in a blue ceramic cup`, other drinks (milk, juice, water, …), quantities and plurals, extra adjectives and colours, two cups or two drinks, a filled cup plus any other object, and a missing table phrase. The whole prompt is refused — the drink is never silently dropped to produce an empty cup.

Model: `CupContents(CeramicInstance Cup, BeverageKind Beverage)` is the only cup-content value, with `BeverageKind` closed to `Coffee` and `Tea`. It refers to the cup instance the scene already holds rather than copying it, so the cup keeps its kind, glaze, body, seed, depth and handle, and the drink is never a second independently positioned scene object with its own shadow. `CupContents` and Phase 5 `BowlContainment` are mutually exclusive, and validation requires exactly one ceramic cup plus one defined beverage.

Surface geometry comes from the cup profile, not from pixel offsets: `CupLiquidSurface` derives the drink's ellipse from `MouthCenter`, `MouthRadius` and `RimThickness`, sinks it slightly below the lip so a crescent of inner wall stays visible above it, and clips it to the inner opening so the lip and rim strokes always stay in front. The surface is deliberately wider than the opening so the drink meets the inner wall instead of floating in a ring of ceramic. It is identical for blue and cream, at every supported seed and at both variation extremes: one fixed, believable fill level, no prompt or UI control.

Rendering inserts the drink into the existing cup mouth stage — after the cavity gradient and inner shading, before the final rim and lip strokes — then keeps the cup's finish sheen off the drink so no glaze can recolour the beverage. Coffee is a dark warm brown with restrained amber sheen; tea is a lighter golden-amber with a darker meniscus. Both use one broad reflection and one glint, and nothing else: no steam, foam, crema art, bubbles or motion. Silhouette and shadow-mask passes are unchanged, so a filled cup silhouettes exactly like the same empty cup, keeps its transparent handle hole, and casts exactly the same tabletop shadow.

Automated coverage: four-combination parser/generator tests, rejection matrix, ordinary-prompt preservation, mutual exclusion with bowl containment, validation of cup and beverage identity, surface bounds and rim margins, glaze/seed/variation independence of the surface, deterministic rendering, non-vacuous in-mouth invariants against the same empty cup (nothing outside the mouth changes, nothing below the horizon changes), coffee-versus-tea luminance separation, glaze-independence of the liquid pixels, silhouette and shadow-mask equality, detail-omission behaviour, diagnostic-pass stability, desktop pipeline and rendered-component prompts, preview retention for rejected prompts, and save-filename whitelisting. With `FORMFLOOM_EXPORT_ALL=1` the export tests also write `formloom-cupliquid-*.png`, `-silhouette.png` and `.timing.json` sidecars that record the equivalent empty-cup timing; routine CI keeps `formloom-cupliquid-sheet.png` (a plain row-major grid), `formloom-cupliquid-sheet.timing.json` and the canonical case.

See the [Phase 6 handoff](docs/cup-liquids-handoff.md) for design decisions, evidence, artifacts and limits, and the [checklist](.agents/todo-6.md).

## Phase 7: a tulip in a ceramic vase

One existing vase holding one tulip. Four combinations: blue and cream vases, each with a red or a yellow tulip.

```
a red tulip in a blue ceramic vase on a wooden table
a red tulip in a cream ceramic vase on a wooden table
a yellow tulip in a blue ceramic vase on a wooden table
a yellow tulip in a cream ceramic vase on a wooden table
```

Grammar is exact: `<a red|a yellow> tulip` + `in` + `<a blue|a cream> ceramic vase` + `on a wooden table`. Case, whitespace and terminal punctuation are normalized as before. Rejected whole rather than simplified: other species (rose, daisy, sunflower, lily, orchid), other colours (pink, white, purple, orange, multicoloured, unspecified), bowls and cups as the container, `inside` / `within` / `with` / `holding` instead of `in`, the reversed `a blue ceramic vase with a red tulip`, quantities and plurals (two tulips, a bunch, a bouquet), two vases, extra adjectives (large, tall), a second object in the scene, and a missing table phrase. The whole prompt is refused — the flower is never silently dropped to produce an empty vase.

Model: `VaseFlower(CeramicInstance Vase, FlowerKind Flower, TulipColor Color, TulipPlant Plant)` is the only vase-content value, with `FlowerKind` closed to `Tulip` and `TulipColor` closed to `Red` and `Yellow`. It refers to the vase instance the scene already holds rather than copying it, so the vase keeps its kind, glaze, body, seed and depth. The flower is not a `SceneEntry`: it has no transform, depth or shadow of its own. `VaseFlower`, `BowlContainment` and `CupContents` are mutually exclusive, and validation requires exactly one ceramic vase in the scene plus one defined flower and colour.

The arrangement is exactly one bloom, one stem and two leaves. `TulipPlant` carries them as scene-normalized geometry: a single softly bent stem, two lance-shaped leaves with a restrained centre vein attached at different heights on the stem, and a cupped bloom of five overlapping petals (two wide back petals, two side petals, one narrow front petal). Everything is derived from the vase profile — the stem enters through the middle of `MouthCenter` and the whole plant is sized from the headroom between the mouth's top edge and a fixed top margin — so no canvas pixel offset is hard-coded and the plant scales with the vase body. Shape variation is bounded, seeded and confined to three named streams (`tulip.stem`, `tulip.leaves`, `tulip.bloom`); it changes the stem's sway, leaf angles and petal jitter, never the species, the colour, the petal count, the leaf count or the bloom count. Red and yellow share identical geometry, and the vase glaze has no influence on the plant at all.

Rendering draws the flower before the vase, clipped to a half-plane taken from the mouth's own top tangent, so nothing can reach the exterior wall or the table. The mouth keeps its own order — cavity base, thin far rim, thick near lip — and the stem's continuation is painted last, after the vase's contour stroke, through a single mask that is the opening inset by the near lip unioned with a narrow column across the rim band. It is the same stroke as the stem above the rim, extended past its typed end, darkened by a vertical gradient that starts transparent at the tangent. Nothing the vase draws crosses it and no two passes meet inside the mouth, so the stem enters the vase as one continuous line instead of being banded by the rim or ending in mid-air. Below the rim, the only pixels that differ from the same empty vase are inside that opening; the vase keeps its own shadow, and the flower adds no tabletop cast shadow of its own. Petals use a value hierarchy — dark back petals, brighter front petals — for the cupped read, with restrained edge separation and no heavy outlines; stem and leaves share one green material with directional shading, so changing the vase's glaze can never recolour the flower. Silhouettes include the bloom, because it is a visible part of the subject: the silhouette of a planted vase is the empty vase's silhouette plus the flower above the rim, and nothing is lost below it. Detail omission on the vase's depth drops the leaf veins and the petal edge strokes without touching any pixel outside the flower.
